// la idea de la noche

Autocomplete predice. Un agent corre un loop.

Esa es la diferencia completa, y es la razón de que se trabaje distinto. Todo lo demás de estas cuatro sesiones cuelga de aquí.

01 · gather

Junta contexto

Lee archivos, busca, corre comandos para entender dónde está parado. Lo que no lee es lo que después te va a costar caro.

02 · act

Actúa

Escribe, edita, ejecuta. Aquí es donde te pide permiso, y donde tú decides qué tanto lo dejas hacer solo.

03 · verify

Verifica

Corre lo que escribió y revisa si funcionó. Es el paso que se salta él, y el que te saltas tú.

Cuando algo sale mal, el diagnóstico empieza aquí: ¿falló el gather (no leyó lo que necesitaba), el act (leyó bien pero hizo mal), o el verify (hizo mal y no se dio cuenta)? Casi siempre es el gather. Eso es la sesión 2.
// por qué hay tantas herramientas

Cuatro capas que se pueden mezclar.

La confusión con los nombres se acaba cuando ves que son capas distintas, no competidores. Casi todo lo que parece una decisión enorme es solo escoger en una capa.

lab        →   Anthropic · OpenAI · Google
model      →   Opus · GPT · Gemini
agent      →   el loop + las tools
interface  →   terminal · GUI · IDE

Un mismo model corre dentro de agents distintos. Un mismo agent se usa desde interfaces distintas. opencode es el ejemplo más claro: es un agent que corre models de varios labs, así que cambiar de model no te obliga a cambiar de herramienta.

Lo que aprendes hoy vive en la capa del agent, que es la que no cambia cuando cambias de proveedor. Por eso vale la pena aprenderla bien una vez.

Las cinco preguntas para cualquier herramienta nueva

Cuando te sientes frente a un agent que no conoces, esto te ubica en dos minutos:

  1. ¿Dónde escribo?
  2. ¿Dónde veo lo que está haciendo?
  3. ¿Dónde me pide permiso?
  4. ¿Dónde veo el diff?
  5. ¿Cómo lo reseteo?

// hora 2 · copia y pega

Tres prompts, no uno.

Un prompt grande te devuelve una caja negra. Tres te dejan ver el loop y revisar cada paso por separado. Córrelos en orden, en tu repo, en el branch nuevo.

P1 Gather - que lea antes de tocar 
Explora este repositorio sin modificar nada.

Explícame:
1. Qué hace este proyecto, en 3 frases.
2. Cuál es el punto de entrada y cómo se ejecuta localmente.
3. Los 5 archivos o carpetas más importantes, y para qué sirve cada uno.
4. Una cosa que te parezca confusa, inconsistente o mal documentada.

No escribas ni modifiques ningún archivo todavía.
Al final, dime exactamente qué archivos leíste para responder esto.
La última línea es la mitad del valor. Te muestra qué entró al context y, sobre todo, qué no leyó. Si contestó sin abrir los archivos que importan, ya sabes por qué la respuesta suena genérica.
P2 Act - que escriba, con la duda a la vista 
Ahora escribe un archivo nuevo llamado ONBOARDING.md en la raíz del repo.

Audiencia: una persona senior que entra al equipo el lunes y nunca vio
este código.
Incluye: qué hace el proyecto, cómo levantarlo paso a paso, la estructura
de carpetas, y las 3 cosas que más confunden a alguien nuevo aquí.

Reglas:
- Solo afirma cosas que puedas verificar leyendo el repo.
- Si no estás seguro de algo, ponlo bajo una sección "## Sin confirmar"
  en vez de inventarlo.
- No modifiques ningún otro archivo.
La sección ## Sin confirmar no evita que invente: hace visible lo que inventó. Es la diferencia entre un error que encuentras hoy y uno que encuentras en producción.
P3 Verify - que se revise como si no fuera suyo 
Revisa el ONBOARDING.md que acabas de escribir como si fueras un reviewer
hostil. Para cada afirmación, busca en el repo la evidencia que la respalda
y cítame archivo y línea. Lístame todo lo que NO puedas respaldar con
evidencia.
Y después la parte que te toca a ti. Corre git status y git diff --stat, lee la sección ## Sin confirmar, y ejecuta un comando del setup que escribió. Si el comando no corre, ahí está tu primer error.

Sin terminal: pídele "enséñame qué archivos cambiaste y el diff de cada uno, y corre el primer comando del setup que escribiste". Apruébale los permisos y lee la salida. Llegas al mismo sitio.
Lo que reportas al final: una cosa que el agent afirmó y que está mal. Una sola. Todo el mundo encuentra una, y eso es justo lo que queremos ver.

¿Ya llevas rato usando agents?

Si los tres de arriba se te hacen cortos, haz este en vez del P2. Mismo loop, más filo: en vez de escribir un documento, el agent cambia código de verdad, y tú decides el alcance antes de que toque nada.

B1 Que proponga - tú escoges 
Sin escribir código todavía: lístame 3 cambios chicos y concretos que
mejorarían este repo. Cada uno tiene que cumplir:
(a) tocar como máximo 2 archivos,
(b) que yo pueda verificar que funciona corriendo un comando,
(c) que no cambie el comportamiento público.

Para cada uno dime qué archivos tocarías y qué comando correría yo
para verificar.
Las tres restricciones son el prompt. Sin ellas, "mejora este repo" te devuelve un refactor de 900 líneas que no vas a revisar y vas a mergear igual.
B2 Que ejecute el que tú escogiste 
Haz el número 2. Cuando termines, dime exactamente qué comando tengo
que correr para verificar que funciona, y qué debería ver si está bien.
Después le corres el P3 igual que todo el mundo, y lees el diff línea por línea. Aquí sí importa: es código que se ejecuta, no prosa.

Reportas lo mismo que los demás: una cosa que hizo mal. En este camino suele estar escondida en un caso borde que el agent no probó.
