// primero · skills

Una skill es un workflow que dejaste escrito.

No es una función ni un plugin. Es un archivo de texto con tres cosas: cómo se llama, cuándo se usa, y los pasos. El agent lo lee cuando la tarea encaja, y hace lo de siempre sin que tú se lo expliques otra vez.

# Revisar un PR de este repo

Cuándo: me pidan revisar un cambio, un diff o un PR de este proyecto.

Pasos:
1. `git diff --stat` primero. Si tocó archivos que nadie pidió, para y dilo.
2. Las cuatro preguntas, en orden: ¿corre? ¿hace lo que se pidió?
   ¿rompe algo? ¿lo puedo mantener?
3. Cada afirmación con archivo y línea. Lo que no puedas citar, va
   aparte bajo "sin confirmar".
4. No arregles nada. Reporta.

Eso es todo. Si lo lees y sabes qué haría el agent, está bien escrito.

Skill y AGENTS.md no compiten. El AGENTS.md entra siempre, así que cada línea te cuesta context en cada sesión - por eso es corto. La skill entra cuando toca, así que puede tener los pasos completos sin estorbarle al resto del trabajo.

Dónde vive, según lo que uses

Aquí está la parte que a mucha gente le sorprendió en vivo: skills es un estándar abierto (agentskills.io). El mismo SKILL.md corre en Claude Code y en Antigravity sin cambiarle una línea. Lo único que cambia es en qué carpeta lo pones.

Lo que usasDónde lo guardas

Otro agent de terminalCasi todos ya leen el estándar. Si el tuyo no, déjalo en el repo - docs/workflows/revisar-pr.md sirve - y pon una línea en el AGENTS.md que diga cuándo leerlo.
Sin terminalEl mismo texto, guardado donde lo tengas a mano para pegarlo. Menos automático, mismo resultado.
Del frontmatter, solo dos cosas importan: name (opcional, si no lo pones agarra el nombre de la carpeta) y description. El description es el que decide si la carga sola o no - es lo único que el agent ve antes de abrir el archivo. Escríbelo como la situación en que se usa, no como el título de lo que hace.
// cuándo algo merece ser skill

La regla de las dos veces.

El homework de anoche era traer algo que hiciste dos veces. Esa es la señal, y no hay que buscarle más:

  1. Lo hiciste dos veces. Los mismos pasos, en el mismo orden, con dos días de diferencia.
  2. Se lo explicaste dos veces. Escribiste el mismo prompt largo en dos sesiones distintas.
  3. Te corrigió lo mismo dos veces. Ahí puede que no sea una skill: puede ser una línea del AGENTS.md.
Cómo escoger entre los dos: si es una regla, va al AGENTS.md. Si son pasos, es una skill. "Los componentes van en src/features/" es regla. "Así reviso un PR aquí" son pasos.

Las que ya están escritas.

La regla de las dos veces sirve para lo tuyo, que es lo que nadie más puede escribir. Pero mucho de lo que ibas a escribir ya existe - y algunas ya las tienes instaladas sin saberlo.

1 · Las que ya vienen puestas

Claude Code trae varias de fábrica. El error más común de la primera semana es escribir una skill para algo que ya venía resuelto:

2 · Las de otra gente

La que se nombró en vivo es la colección de Matt Pocock. No son de "vibe coding": son de trabajo aburrido y real - tdd, code-review, diagnosing-bugs, handoff, research.

La que vale la pena mirar primero es grill-me: te entrevista sobre tu plan hasta que no quede nada sin decidir, antes de dejar que se escriba código. Es lo contrario de lo que hace la gente con un agent, y por eso funciona.

3 · El repo que enseña la diferencia

El otro que salió es andrej-karpathy-skills: cuatro reglas sacadas de lo que Karpathy ha dicho sobre cómo fallan los LLM escribiendo código. Think Before Coding, Simplicity First, Surgical Changes, Goal-Driven Execution.

Lo interesante no son las reglas. Es que el repo trae el mismo contenido empaquetado de las dos maneras, y te deja escoger:

  1. Un CLAUDE.md que bajas con curl y entra siempre, en cada sesión de ese proyecto.
  2. Un skills/karpathy-guidelines/SKILL.md que se instala como plugin y entra cuando toca.
Eso es exactamente lo de arriba, en un repo real. El mismo texto cuesta context distinto según dónde lo pongas. Si quieres que esas cuatro reglas apliquen a todo lo que escribas, va al archivo que entra siempre. Si solo aplican cuando estás refactorizando, va a la skill. La decisión es tuya, y el repo no la toma por ti.

Ojo con el nombre, que confunde: se llama skills y arrancó siendo un CLAUDE.md. El install del README apunta a forrestchang/andrej-karpathy-skills, que es de donde salió.

// la palabra que faltaba

Y entonces, ¿qué es un plugin?

Una skill es un archivo. Un plugin es la caja en la que alguien te manda varias, más los MCP que hacen falta y la configuración que las hace funcionar. Es cómo la gente comparte su setup completo en vez de mandarte instrucciones.

Y no hay una tienda oficial de nadie: un marketplace es un repo de git con un archivo .claude-plugin/marketplace.json. Cualquiera publica el suyo, y tú lo agregas:

/plugin marketplace add <usuario>/<repo>
/plugin install <nombre>@<marketplace>

El caso que se mencionó es gstack, de Garry Tan - el presidente de Y Combinator. Publicó su setup exacto de Claude Code: veintitrés comandos que hacen de CEO, de eng manager, de diseñador, de QA y de release manager. Se instala pegándole una línea al agent y él hace el resto.

Lo mismo que con los MCP: instalar el setup de otro no te da su criterio. Veintitrés comandos nuevos son veintitrés descripciones que tu agent tiene que leer para escoger, y tú no sabes qué hace ninguno. Instala uno, úsalo una semana, y después mira el segundo. Es el mismo consejo de la sección de MCP, por la misma razón.
// segundo · MCP

MCP es cómo el agent alcanza lo de afuera.

Hasta hoy, sus tools eran las de fábrica: leer archivos, editar, correr comandos. Todas dentro de tu repo. MCP es el estándar que le conecta otras - tu correo, tu calendario, una base de datos, lo que tenga un server - sin que nadie tenga que programar una integración a medida para cada agent.

01 · el server

Quién ofrece

Un programa que dice "yo sé hacer estas cosas". Puede correr en tu máquina o estar en la nube.

02 · las tools

Qué puede hacer

Cada server expone una lista: buscar_correo, crear_evento. El agent escoge cuál usar, igual que con las de fábrica.

03 · el permiso

Quién aprueba

Sigue siendo tuyo. El agent pide, tú apruebas. Con tools que mandan correos, eso deja de ser un detalle.

Cada MCP que conectas te cuesta context. La lista de tools viaja en cada llamada, con nombre, descripción y parámetros. Conecta lo que vas a usar hoy, no todo lo que existe: veinte servers conectados es menos sitio para tu código, y un agent que escoge peor porque tiene cien tools donde le bastaban seis.
// la pregunta de la noche

¿Y cuál conecto?

La pregunta que salió apenas se entendió qué era MCP. La respuesta útil no es una lista de los más descargados - es esta división, porque cambia cómo los apruebas y cuánto te puede doler un error.

los que leen

Traen contexto que tú pegabas a mano

El issue tracker, la base de datos, los logs y errores de producción, los diseños, tu correo y tu calendario. Lo peor que pasa es que lea algo que no debía.

los que escriben

Hacen cosas que se ven afuera

Abrir un PR, mandar un mensaje, crear un evento, tocar la base de datos. Aquí un error no se queda en tu pantalla: lo ve otra gente.

el que casi todos quieren

El browser

Que abra la página y compruebe que el cambio se ve bien. Es el que más rápido convence, y el que más context se come.

Casi todos los servers son las dos cosas a la vez. El mismo server de correo tiene search_threads, que solo lee, y create_draft, que escribe. Por eso el P3 te hace listarlas y separarlas antes de darle una tarea: no se aprueba un server, se aprueban tools.

La señal para conectar uno: te viste copiando y pegando datos de esa herramienta al chat, más de una vez. Esa es la misma regla de las dos veces, aplicada a las tools en vez de a los workflows. Si no lo has pegado nunca, no lo conectes todavía.

Crea tu companion diario.

Junta las dos mitades de la noche. El MCP le da acceso a tu correo y a tu calendario; la skill le dice qué hacer con eso. El resultado es una pregunta que le haces cada mañana - "¿qué tengo hoy?" - y un brief de veinte líneas en vez de veinte minutos revisando el inbox.

Paso 1 · Conectarle Gmail y Calendar

Hay dos caminos. El corto es de una vez; el completo pide más trabajo pero es el único que sirve igual en las dos herramientas.

El camino corto - Claude Code: ya viene con los connectors de Google puestos, no hay que instalar nada.

/mcp

Sale la lista, escoges Gmail y Google Calendar, se abre el browser, entras con tu cuenta y ya. Sin proyecto de Google Cloud, sin claves. Es lo que se hizo en pantalla esa noche.

El camino completo - los servers oficiales de Google: los mismos que usa todo el mundo, conectados con tu propia credencial. Es el camino de Antigravity, y también el tuyo si tu cuenta del trabajo bloquea lo demás.

ServerLa URL que le pegas
Gmailhttps://gmailmcp.googleapis.com/mcp/v1
Calendarhttps://calendarmcp.googleapis.com/mcp/v1

Antes de pegar nada, en Google Cloud Console: creas un proyecto, prendes la Gmail API y la Gmail MCP API (lo mismo con las dos de Calendar), configuras la pantalla de consentimiento con los scopes que pide cada una, y creas un OAuth client. De ahí salen el clientId y el clientSecret.

Los scopes son de lectura, salvo uno: Gmail pide gmail.readonly y gmail.compose - el segundo es el que le deja escribir borradores. Calendar pide tres, y las tres son readonly. Léelos: es la única vez que vas a ver en una pantalla, sin adornos, exactamente qué puede tocar.

Después, en Claude Code:

claude mcp add --transport http gmail https://gmailmcp.googleapis.com/mcp/v1
claude mcp add --transport http calendar https://calendarmcp.googleapis.com/mcp/v1

Y en Antigravity, escribes /mcp y usas el manager, o editas el archivo a mano:

{
  "mcpServers": {
    "gmail": {
      "serverUrl": "https://gmailmcp.googleapis.com/mcp/v1",
      "oauth": { "clientId": "TU_CLIENT_ID", "clientSecret": "TU_SECRET" }
    },
    "calendar": {
      "serverUrl": "https://calendarmcp.googleapis.com/mcp/v1",
      "oauth": { "clientId": "TU_CLIENT_ID", "clientSecret": "TU_SECRET" }
    }
  }
}
Dónde va ese archivoRuta
Para todo lo que hagas~/.gemini/config/mcp_config.json
Solo para este proyecto.agents/mcp_config.json

En el IDE lo abres sin buscarlo: el menú … arriba del panel del agent → MCP Servers → Manage MCP Servers → View raw config. Guardas y recarga solo.

Ese archivo termina con tu clientSecret dentro. Si lo pusiste en .agents/, que es carpeta del proyecto, revisa que no se te vaya en un commit. Antigravity acepta ${VARIABLE} para no escribir el secreto ahí; úsalo si el repo lo comparte alguien más.

Paso 2 · La skill

Con los MCP conectados, el agent puede leer tu correo. Todavía no sabe qué te importa. Eso es la skill, y es el archivo que te llevas de esta semana:

SKILL brief-diario - el companion completo 
---
name: brief-diario
description: Arma el brief de la mañana cruzando el calendario de hoy con el
  correo sin contestar. Úsala cuando pregunte qué tengo hoy, qué se me quedó
  sin responder, qué se me está acumulando, o cuando pida el brief.
---

# Brief diario

Solo lees. No mandas correos, no creas eventos, no marcas nada.

## Pasos

1. Calendario de hoy. Lista los eventos de ahora hasta que termine el día.
   Guarda hora, título y quién más está invitado. Si dos se pisan, anótalo.
2. Las cadenas de correos de las últimas 48 horas. Filtra desde la búsqueda:
   in:inbox newer_than:2d category:primary -from:noreply -list:*
   Después, a mano: fuera los avisos del banco, los recibos y los bots.
   Fuera también la cadena donde el último mensaje es tuyo.
3. Cruza las dos listas. Un correo de alguien con quien tienes reunión hoy
   sube al tope: eso es lo que te va a caer encima en la reunión.
4. Escribe el brief, en este orden y nada más:
   - HOY: los eventos con su hora. Marca al que hay que llegar preparado.
   - ESPERAN POR TI: máximo 5 cadenas. De quién, de qué, hace cuánto.
   - OJO: lo que se pisa, lo que lleva días parado, lo que se repite.
5. Lo que no puedas verificar va aparte, bajo "Sin confirmar". No adivines
   qué se decidió en una cadena: si hace falta abrirla para saberlo, dilo.

## Reglas

- Máximo 20 líneas. Esto se lee de pie, con el café en la otra mano.
- Nombres y asuntos tal como están, sin resumirlos hasta que no se entiendan.
- Si te pido actuar sobre algo del brief, lo dejas en draft. Mandar lo hago yo.
- Si no queda nada después de filtrar, dilo. "Hoy nadie espera por ti" es un
  brief correcto. Rellenar con newsletters para que se vea lleno, no.
El description es la mitad del archivo. Fíjate que no dice qué hace la skill, dice en qué situación estás tú cuando hace falta - "qué tengo hoy", "qué se me quedó sin responder". Eso es lo único que el agent lee para decidir si abrirla. Un description escrito como título ("Genera un resumen diario") no dispara nunca.

Lo guardas donde lo busque tu agent, según la tabla de arriba. Para que sirva en todos tus proyectos y no solo en uno:

# y pegas el archivo como SKILL.md ahí dentro

# Antigravity

Paso 3 · Probarla en sesión limpia

Lo mismo que el martes con el AGENTS.md, y por la misma razón. Si la pruebas en la sesión donde la escribiste, el agent ya tiene los pasos en context y los sigue aunque el archivo esté vacío. No probaste nada.

Cierra. Abre otra. Escribe "¿qué tengo hoy?" y no menciones la skill. Si la carga sola, quedó. Si no, el description está escrito como título y hay que reescribirlo - que fue lo que le pasó a media sala.

Lo que pasó cuando se corrió en vivo, y vale más que el ejemplo bonito de arriba. La primera versión del paso 2 buscaba "el correo de los últimos dos días" sin filtrar: 201 cadenas de correos, de las cuales ni una era una persona esperando respuesta. Eran avisos del banco, recibos de Uber, newsletters y bots de GitHub comentando un PR. Con el filtro que está arriba, los mismos dos días bajan a 2. La skill no sirvió hasta la segunda versión, y esa segunda versión salió de mirar el output malo. Esto no es el paso raro: es el paso.

Paso 4 · Que corra solo (opcional)

Pedírselo tú cada mañana ya sirve, y es como empieza todo el mundo. Cuando lleves varios días leyéndolo de verdad, entonces sí:

HerramientaCómo se programa
Claude CodeSe lo pides con palabras en cualquier sesión: "prográmame esto todos los días a las 7am". La tarea que guarda es - otra vez - un SKILL.md, en ~/.claude/scheduled-tasks/. Corre en tu máquina: necesita la app abierta y la computadora despierta.
AntigravityScheduled Tasks: le pones horario, prompt y proyecto, y el agent arranca solo en el fondo. La conversación te aparece después en el sidebar.
Cualquier otroSi corre desde el terminal, un cron que lo llame y te mande la salida hace lo mismo.

Ojo con la hora. Una tarea de las 7am puede correr a las 11pm si la máquina estuvo dormida. La guardia va dentro de la skill, no en el horario: "si ya pasaron las 10am, dilo en la primera línea".

Automatizarlo sube la apuesta. Un brief que sale solo lo lees en diagonal a los tres días. Y un agent que corre sin que tú estés mirando es exactamente donde "nada se manda sin que tú lo leas" deja de ser un consejo y pasa a ser lo único que te protege. Empieza pidiéndolo a mano. Automatiza cuando ya sepas que el brief te sirve.
Y las dos que no se negocian, otra vez. Lo que el agent lee de tu correo entra al context: no conectes la cuenta que tiene cosas que no le enseñarías a una herramienta - y si esa es tu cuenta del trabajo, esa es la respuesta. Y nada se manda sin que tú lo leas: por eso la skill dice draft y no enviar. Un agent que puede escribir correos y ejecutar sin permiso es la peor combinación de la semana.

// hora 2 · copia y pega

Tres prompts: encontrar, escribir, conectar.

El primero busca lo que repetiste esta semana, el segundo lo convierte en archivo, y el tercero le da al agent una tool que no tenía.

P1 Encontrar - qué repetiste 
Te voy a describir lo que hice contigo esta semana. Dime qué partes
son un workflow que se repite y cuáles fueron de una sola vez.

[pega aquí, en dos o tres líneas, lo que le pediste más de una vez]

Para cada workflow que encuentres:
1. Ponle un nombre corto.
2. Dime en qué situación se debería usar, en una frase.
3. Lista los pasos, en orden, como se los darías a alguien que
   nunca lo ha hecho.

No inventes workflows para llenar la lista. Si solo hay uno, dime uno.
El "no inventes" hace el trabajo. Sin esa línea te devuelve cinco workflows genéricos que suenan bien y no son tuyos. Con ella suele devolver uno o dos, y son los que de verdad repetiste.
P2 Escribir - la skill, corta 
Escribe ese workflow como un archivo de instrucciones para ti mismo,
de máximo 25 líneas, con esta forma:

- Un título de una línea.
- "Cuándo:" una frase que diga en qué situación se usa.
- "Pasos:" la lista, en orden, con lo que hay que verificar en cada uno.

Reglas:
- Nada de consejos genéricos. Solo lo que aplica a este proyecto.
- Si un paso depende de algo que no sabes, no lo adivines: déjalo
  como pregunta al final, fuera del archivo.
- Escríbelo para que sirva dentro de seis meses, cuando ninguno de
  los dos se acuerde de esta conversación.
Las preguntas del final valen más que el archivo. Son exactamente lo que tú sabías y nunca escribiste en ningún lado. Contéstalas dentro del archivo y ya tienes la segunda versión.
P3 Conectar - que use una tool nueva 
Ya tienes conectado un MCP nuevo. Antes de que te pida nada con él:

1. Lístame las tools que te dio, con lo que hace cada una en una línea.
2. Dime cuáles de ellas pueden cambiar o borrar algo, y cuáles solo leen.
3. Escoge la tarea más chica que puedas hacer con las de solo lectura,
   hazla, y muéstrame el resultado.

Después de eso, y no antes, seguimos con lo demás.
El paso 2 es el que importa. Saber cuáles tools escriben - antes de darle una tarea - es la diferencia entre aprobar permisos leyendo y aprobar permisos por cansancio. Es lo mismo que hiciste con el diff anoche, aplicado a las herramientas.

Dónde un agent es la herramienta equivocada.

Cuatro noches diciendo cómo sacarle trabajo. Esta parte también es del curso:

  1. Cuando no puedes verificar el resultado. Si no sabes cómo comprobar que está bien, no importa lo rápido que salga.
  2. Cuando el error no tiene vuelta atrás. Migraciones de datos, cosas que salen a producción sin revisión, todo lo que se manda a un cliente. El loop del agent no sabe de consecuencias.
  3. Cuando el problema es decidir, no ejecutar. Te va a dar una respuesta segura para una pregunta que todavía no está decidida. Eso no es ayuda, es ruido con formato.
  4. Cuando el trabajo es aprender. Si lo que necesitas es entender esa parte del sistema, que lo escriba él es exactamente lo contrario de lo que te hace falta.
La señal más barata: si no sabrías decir por qué el resultado está bien, todavía no terminaste - da igual quién lo escribió.

Que no se te olvide.

Ya sabes las cuatro: correr el loop, darle context, revisar lo que devuelve, y dejarlo escrito. Lo que sigue no es otro curso, son tres cosas chiquitas:

  1. Una línea más al AGENTS.md cada vez que el agent haga algo que te dé rabia.
  2. Una skill más cuando te veas escribiendo el mismo prompt largo por segunda vez.
  3. Un MCP, el que uses de verdad. Uno. Cuando ese te sirva, piensa en el segundo.
Las cuatro páginas se quedan aquí, con los prompts y los archivos, sin fecha de vencimiento. El kit es el que vas a abrir más veces.
