// primero · skills

Una skill es un workflow que dejaste escrito.

No es una función ni un plugin. Es un archivo de texto con tres cosas: cómo se llama, cuándo se usa, y los pasos. El agent lo lee cuando la tarea encaja, y hace lo de siempre sin que tú se lo expliques otra vez.

# Revisar un PR de este repo

Cuándo: me pidan revisar un cambio, un diff o un PR de este proyecto.

Pasos:
1. `git diff --stat` primero. Si tocó archivos que nadie pidió, para y dilo.
2. Las cuatro preguntas, en orden: ¿corre? ¿hace lo que se pidió?
   ¿rompe algo? ¿lo puedo mantener?
3. Cada afirmación con archivo y línea. Lo que no puedas citar, va
   aparte bajo "sin confirmar".
4. No arregles nada. Reporta.

Eso es todo. Si lo lees y sabes qué haría el agent, está bien escrito.

Skill y AGENTS.md no compiten. El AGENTS.md entra siempre, así que cada línea te cuesta context en cada sesión - por eso es corto. La skill entra cuando toca, así que puede tener los pasos completos sin estorbarle al resto del trabajo.

Dónde vive, según lo que uses

El nombre cambia, la idea no: un archivo que el agent encuentra solo, en vez de un prompt que pegas a mano.

// cuándo algo merece ser skill

La regla de las dos veces.

El homework de anoche era traer algo que hiciste dos veces. Esa es la señal, y no hay que buscarle más:

  1. Lo hiciste dos veces. Los mismos pasos, en el mismo orden, con dos días de diferencia.
  2. Se lo explicaste dos veces. Escribiste el mismo prompt largo en dos sesiones distintas.
  3. Te corrigió lo mismo dos veces. Ahí puede que no sea una skill: puede ser una línea del AGENTS.md.
Cómo escoger entre los dos: si es una regla, va al AGENTS.md. Si son pasos, es una skill. "Los componentes van en src/features/" es regla. "Así reviso un PR aquí" son pasos.
// segundo · MCP

MCP es cómo el agent alcanza lo de afuera.

Hasta hoy, sus tools eran las de fábrica: leer archivos, editar, correr comandos. Todas dentro de tu repo. MCP es el estándar que le conecta otras - tu correo, tu calendario, una base de datos, lo que tenga un server - sin que nadie tenga que programar una integración a medida para cada agent.

01 · el server

Quién ofrece

Un programa que dice "yo sé hacer estas cosas". Puede correr en tu máquina o estar en la nube.

02 · las tools

Qué puede hacer

Cada server expone una lista: buscar_correo, crear_evento. El agent escoge cuál usar, igual que con las de fábrica.

03 · el permiso

Quién aprueba

Sigue siendo tuyo. El agent pide, tú apruebas. Con tools que mandan correos, eso deja de ser un detalle.

Cada MCP que conectas te cuesta context. La lista de tools viaja en cada llamada, con nombre, descripción y parámetros. Conecta lo que vas a usar hoy, no todo lo que existe: veinte servers conectados es menos sitio para tu código, y un agent que escoge peor porque tiene cien tools donde le bastaban seis.
// el caso de la noche

Tu correo y tu calendario, leídos por el agent.

Esto lo corro yo en vivo, con mi cuenta - conectar Google en veinte máquinas a la vez se come la sesión, y a algunos su cuenta del trabajo se lo bloquea. Tú miras el flujo completo, y en la hora 2 haces lo mismo con un MCP local que no pide OAuth.

  1. Conectar. El server de correo y el de calendario, y ver la lista de tools que aparecen.
  2. Preguntar. Qué hay esta semana, qué quedó sin contestar, qué se repite.
  3. Hacer algo con eso. Un borrador, un resumen, un evento propuesto. Nunca enviado: propuesto.
  4. Revisarlo. Con las cuatro preguntas de anoche, antes de que salga de tu pantalla.
Dos cosas que no se negocian. Lo que el agent lee de tu correo entra al context, así que no conectes la cuenta con cosas que no le enseñarías a una herramienta. Y nada se manda sin que tú lo leas: un agent que puede escribir correos y ejecutar sin permiso es la peor combinación de la semana.
// hora 2 · copia y pega

Tres prompts: encontrar, escribir, conectar.

El primero busca lo que repetiste esta semana, el segundo lo convierte en archivo, y el tercero le da al agent una tool que no tenía.

P1 Encontrar - qué repetiste 
Te voy a describir lo que hice contigo esta semana. Dime qué partes
son un workflow que se repite y cuáles fueron de una sola vez.

[pega aquí, en dos o tres líneas, lo que le pediste más de una vez]

Para cada workflow que encuentres:
1. Ponle un nombre corto.
2. Dime en qué situación se debería usar, en una frase.
3. Lista los pasos, en orden, como se los darías a alguien que
   nunca lo ha hecho.

No inventes workflows para llenar la lista. Si solo hay uno, dime uno.
El "no inventes" hace el trabajo. Sin esa línea te devuelve cinco workflows genéricos que suenan bien y no son tuyos. Con ella suele devolver uno o dos, y son los que de verdad repetiste.
P2 Escribir - la skill, corta 
Escribe ese workflow como un archivo de instrucciones para ti mismo,
de máximo 25 líneas, con esta forma:

- Un título de una línea.
- "Cuándo:" una frase que diga en qué situación se usa.
- "Pasos:" la lista, en orden, con lo que hay que verificar en cada uno.

Reglas:
- Nada de consejos genéricos. Solo lo que aplica a este proyecto.
- Si un paso depende de algo que no sabes, no lo adivines: déjalo
  como pregunta al final, fuera del archivo.
- Escríbelo para que sirva dentro de seis meses, cuando ninguno de
  los dos se acuerde de esta conversación.
Las preguntas del final valen más que el archivo. Son exactamente lo que tú sabías y nunca escribiste en ningún lado. Contéstalas dentro del archivo y ya tienes la segunda versión.
P3 Conectar - que use una tool nueva 
Ya tienes conectado un MCP nuevo. Antes de que te pida nada con él:

1. Lístame las tools que te dio, con lo que hace cada una en una línea.
2. Dime cuáles de ellas pueden cambiar o borrar algo, y cuáles solo leen.
3. Escoge la tarea más chica que puedas hacer con las de solo lectura,
   hazla, y muéstrame el resultado.

Después de eso, y no antes, seguimos con lo demás.
El paso 2 es el que importa. Saber cuáles tools escriben - antes de darle una tarea - es la diferencia entre aprobar permisos leyendo y aprobar permisos por cansancio. Es lo mismo que hiciste con el diff anoche, aplicado a las herramientas.
// dónde no

Dónde un agent es la herramienta equivocada.

Cuatro noches diciendo cómo sacarle trabajo. Esta parte también es del curso:

  1. Cuando no puedes verificar el resultado. Si no sabes cómo comprobar que está bien, no importa lo rápido que salga.
  2. Cuando el error no tiene vuelta atrás. Migraciones de datos, cosas que salen a producción sin revisión, todo lo que se manda a un cliente. El loop del agent no sabe de consecuencias.
  3. Cuando el problema es decidir, no ejecutar. Te va a dar una respuesta segura para una pregunta que todavía no está decidida. Eso no es ayuda, es ruido con formato.
  4. Cuando el trabajo es aprender. Si lo que necesitas es entender esa parte del sistema, que lo escriba él es exactamente lo contrario de lo que te hace falta.
La señal más barata: si no sabrías decir por qué el resultado está bien, todavía no terminaste - da igual quién lo escribió.
// después de esta semana

Que quede.

Ya sabes las cuatro: correr el loop, darle context, revisar lo que devuelve, y dejarlo escrito. Lo que sigue no es otro curso, son tres cosas chiquitas:

  1. Una línea más al AGENTS.md cada vez que el agent haga algo que te dé rabia.
  2. Una skill más cuando te veas escribiendo el mismo prompt largo por segunda vez.
  3. Un MCP, el que uses de verdad. Uno. Cuando ese te sirva, piensa en el segundo.
Las cuatro páginas se quedan aquí, con los prompts y los archivos, sin fecha de vencimiento. El kit es el que vas a abrir más veces.
